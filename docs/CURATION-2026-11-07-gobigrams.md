# Curation — what Gobigrams taught gobstack (2026-11-07)

One project, mined for rules that are true beyond it. This file is the analysis, not the adoption: every proposal
below is stated so it can be argued with, priced, or refused on the record.

**Evidence base.** `diagram-studio` → Gobigrams, 2026-10-23 → 2026-11-07: ~35 rounds, four publish cycles
(0.4.0 → 0.4.5), one npm scope move, three adapters over one core (web app, MCP server, Obsidian plugin), one
renderer extracted into `@techgoblin/gobi-core`, and a launch on a public URL. Numbers quoted here were measured
in that repo; the commits named are the ones that carry them.

---

## 1. The twelve candidates, ranked by leverage

| # | Lesson | Class | Mechanisable today | Verdict |
|---|---|---|---|---|
| C1 | A check's input must come from the producer the user's input comes from | verification | yes, text probe | **adopt** |
| C2 | A measurement must prove its own instrument first | verification | yes, text probe | **adopt** |
| C3 | Cancelled is not pending | handoff | yes, awk probe | **adopt** |
| C4 | A release claim names the artifact the user downloads + one number inside it | release | yes, gate | **adopt** |
| C5 | An artifact declares, inside itself, what it was built from | versioning | yes, gate | **adopt** |
| C6 | Instruction files change only with a recorded approval | governance | yes, hash record | **adopt** |
| C7 | Two agents disagreeing is settled by one written recipe, not a third opinion | process | no | advisory |
| C8 | An advertised capability must be reachable in N actions | product | partly | advisory |
| C9 | Generated state needs retention, and harnesses write only in a scratch namespace | hygiene | yes | later (needs a data-dir concept gobstack does not have) |
| C10 | A gate parsing a tool's output must fail with a named cause, and be proven under every version in play | gate robustness | partly | advisory |
| C11 | One core, N adapters, one conformance corpus that ships with the core | architecture | partly | advisory (class-shaped, not check-shaped) |
| C12 | Every surface that draws a thing must be proven to draw it, not just to compute it | verification | no | rejected for now — see §5 |

## 2. The five adoptions, with the failure that justifies each

### C1 — the payload the check uses must be the payload the user gets

**Failure.** `round-embed-fit` read 10/10 green while the product clipped a 6-node diagram inside an 800×450
iframe. The harness built its fixture with **declared node sizes**; the payload a user actually shares comes from
`compileGobi()` → `toBoardDoc()` and carries **none**. Two different inputs, one green light, one broken product.

**Rule (project-independent).** *A check that asserts a user-visible outcome constructs its input through the same
producer the user's input comes through; a fixture typed by hand is generated by that producer and pinned.*

**Mechanism.** `HV-01`, lint over the harness tree. The probe reads every file that renders, parses or compiles
product input and asserts it either imports the production producer or carries a `produced_by:` marker naming the
producer plus a pinned id. Honest limit (goes in the row's `if_not_why`): it proves the producer is *named and
reachable*, not that the call path matches the product's wiring — a stronger version needs the product to export a
single "make me the thing a user would get" factory, which is a design change, not a probe.

### C2 — a measurement proves its instrument before it accuses the product

**Failure, in three acts.** (a) The orchestrator's browser window was **780×437** while the iframe under test was
**802×452**; every screenshot cut the frame's bottom edge, and the vision read called that "the diagram is
clipped". The product was reported broken **three times**, and four coder rounds were spent chasing a defect that
did not exist — the final numbers were `matrix(0.427527,…)`, 6 nodes, `bbox 251,43 → 529,394`, all inside
780×437. (b) `Emulation.setDeviceMetricsOverride` silently did not change `innerWidth` in a fresh session, so the
instrument believed it had a viewport it did not have. (c) Earlier in the same project, a venv hid `fontTools`, the
probe printed `NaNpx`, and two harnesses convicted a layout that was fine (`ec7077b`).

**Rule.** *A number taken from a live surface carries its guard: a bounding box is asserted inside the capture
viewport, a measurement is asserted non-`NaN` and non-zero, and a missing dependency raises a named error instead
of degrading to a default.*

**Mechanism.** `HV-02`, lint. Files calling `getBoundingClientRect()` must also reference `innerWidth`/`innerHeight`
(or carry `guarded:`), and files that shell out to a text-metrics tool must raise a named missing-module error.
Honest limit: it cannot tell a correct guard from a decorative one.

### C3 — cancelled is not pending

**Failure.** Phase 7 ("five real users") sat in the handoff as an open item for a week after Harvey had decided the
first release did not need strangers. The queue lied: any agent reading the handoff saw work that would never be
done, and every status report inherited the lie.

**Rule.** *Every item in the handoff's NEXT STEPS is one of three shapes: owned with a date, done with evidence, or
cancelled with a date and the decision verbatim. "Open" is not a shape.*

**Mechanism.** `FM-03`… numbered `HP-06` in the matrix (HP is the handoff family): awk over the `NEXT STEPS`
section, each bullet must contain a date and one of `owner`/`done`/`cancelled`. Cheap, deterministic, impossible to
game without writing something true.

### C4 — a release is verified at the layer the user touches, by a number

**Failure.** `sha(build) == sha(deployed)` proved the *deploy*, not the *behaviour*; the same night, a renderer
defect that only appeared in the downloaded SVG was found by Harvey in production (`9c3b0cc`). Symmetrically, the
npm publish was "done" while the registry still served the old version for ~90 s, and an install from the registry
was what settled it.

**Rule.** *A release record names the artifact the user downloads (URL or path), its sha256, and one assertion
measured **inside** that artifact — not in the tree it was built from.*

**Mechanism.** `RL-01`, gate over `.gob/release-record.tsv`:
`date · artifact · sha256 · assertion · command`. The gate checks the file exists, each row has all five fields,
the date is measured, and the sha256 column hashes the same length as the artifact. It cannot re-download the
artifact (that is a network act); it forces the *shape* of the claim, which is what was missing.

### C5 — an artifact says what it was built from

**Failure.** The Obsidian plugin on the store was `0.1.0` built against core `0.4.3` while the app ran `0.4.5`;
three renderer fixes were invisible to every plugin user and nothing in the release said so. The fix that made it
visible was a marker string inside the bundle: `gobi-core:0.4.5 9674bc0`, verified by downloading the release asset
and grepping it.

**Rule.** *Every built artifact embeds `<dependency>:<version> <source-sha>`, machine-readable, and the version gate
compares that marker with the declared dependency.*

**Mechanism.** `VR-01` (new versioning family), gate: for each declared artifact in the project config, grep the
built file for the marker pattern and compare against the lockstep table. This is the single cheapest defence
against "the fix is in the repo but not in the thing people installed".

### C6 — instruction files change only with a recorded approval

**Failure.** Mid-run, the coder could not write the measured placement rule into `AGENTS.md`; the confirmation
dialog timed out and the work stalled until Harvey pressed Allow. Good outcome, no record: nothing in the repo says
who approved that edit or when, and nothing would have noticed if an agent had written it silently.

**Rule.** *`AGENTS.md` (and any file the agent reads as instructions) is hashed into an approval record; an edit
without a matching re-approval is red.*

**Mechanism.** `AG-01`, script: `.gob/agents.approved` holds `sha256 · date · approver · one-line reason`;
`goblin-verify --only AG-01` recomputes. Same shape as `IN-02`, applied to the file that governs the agent.

## 3. The advisory set (no mechanism yet, and why)

- **C7 — the tie-breaker recipe.** When two agents' numbers disagree, the fix that worked was *one recipe both
  sides run*: cross-origin host page, built dist, the payload a user produces, both numbers pasted. Writing a
  "recipe" as a check is not possible; the honest form is a sentence in the `practice` skill plus a template.
- **C8 — advertised capability is reachable.** Gobigrams hit the *seventh* instance of "the capability exists and
  nothing surfaces it" (custom colour: model accepted a hex, `resolveColorKey` returned null, `swatchRow` had an
  unused parameter, no UI reached any of it). The reverse also bit: a help sheet advertising four capabilities that
  the product did not need. A check would need a per-surface definition of "reachable"; keep it as a review
  question with a number ("N actions from a cold start").
- **C10 — tool-output shape.** `npm pack --dry-run --json` changed from an array to an object between npm 11 and
  12; the publish guard read `[0].files`, died, and reported **six** failures that were one failure
  (`f36c7af`). The lesson generalises to every gate that parses another tool: accept the shapes in play, fail with
  a named cause, and prove the gate under each version. Partly mechanisable (the named-cause half), not worth a
  row yet.
- **C11 — one core, N adapters.** The pattern that held: the corpus travelled *with* the package (24 → 26
  fixtures), and every adapter was proven byte-identical against it — app, MCP server, Obsidian plugin. A check
  cannot decide whether a project has one core; it can only verify the corpus is versioned with it. Belongs in the
  architect spec template, not the matrix.

## 4. Where these should live, concretely

| Proposal | Matrix row | Skill touch | Doc touch |
|---|---|---|---|
| C1 | `HV-01` (target, lint) | `goblin-verify-author`: "pick the input the user gets" | LIMITS: what the probe cannot see |
| C2 | `HV-02` (target, lint) | `goblin-verify-author`: "the instrument first" | LIMITS: guards can be decorative |
| C3 | `HP-06` (target, lint) | `goblin-handoff`: the three bullet shapes | GUIDE §8 (keeping HANDOFF honest) |
| C4 | `RL-01` (target, gate) | `goblin-verify-author`: release record | GUIDE §11 reference: `.gob/release-record.tsv` |
| C5 | `VR-01` (target, gate) | `goblin-bootstrap`: markers in built artifacts | GUIDE §4 (Step 2 — commit, then verify) |
| C6 | `AG-01` (target, script) | `goblin-bootstrap` | LIMITS: approval is a hash, not a signature |

Cost estimate, from the shape of the existing checks: `HP-06` and `AG-01` are an afternoon each (awk + a hash
file + one negative-control test each). `HV-01`/`HV-02` are text probes, same class as `BN-*`, two hours each
including a control. `RL-01` and `VR-01` need a small config surface (`.gob/release-record.tsv`, an `artifacts:`
block in the one config) — that is a design decision before it is a probe.

## 5. What this project must NOT push into gobstack

Saying no is half of curation. These are Gobigrams facts with no general form:

- The `.gobi` grammar, its closed-world rule, the shape palette, the layout constants. Product, not practice.
- React Flow pins, byte budgets, the `client_js_bytes` ceiling. Ratchets are per-project policy.
- The publish allowlist and the Forgejo→GitHub snapshot. It is one answer to "public repo from a private workshop",
  shaped by Harvey's hosting choice.
- The three-surface conformance *numbers* (24/26 fixtures). The **pattern** is worth keeping (C11); the numbers are
  not.

## 6. Decisions taken (Harvey: "làm sao theo ý bạn")

Both open questions are answered here rather than left hanging, and the order of work is fixed.

1. **gobstack gets a release family — but opt-in.** `RL-01`/`VR-01` were the whole argument for a fifth family, and
   the argument holds: the gap that produced the plugin-bundling-an-old-core incident is real and general. But not
   every project ships an artifact — a library workspace has nothing to download, and a mandatory release record
   would manufacture red for a non-problem. So the family is declared in the one config (`artifacts:` block plus
   `.gob/release-record.tsv`); a repo without that block gets `SKIP` with the reason, exactly the way `IN-01`
   already skips a declaration-only repo.
2. **C2 is a text probe now, and the limit is stated out loud.** A probe can prove a guard is *present*, not that it
   is *effective*. That is the same honest boundary `BN-01` already draws ("text probe, not an AST"), and it is
   enough to catch the failure that actually happened — a measurement reported with no viewport assertion at all.
   A runtime helper becomes worth its cost only when a project already owns a shared harness library; until then,
   shipping one would bind gobstack to a language for a benefit no check can measure.

**Order of work, cheapest and most preventative first.**

| Phase | Rules | Why this order |
|---|---|---|
| 1 (now) | `HV-02`, `HP-06`, `HV-01` | an afternoon of probes with negative controls; kills the two failure classes that cost the most (a false accusation, and a queue that lies) |
| 2 | `AG-01` | same shape as `IN-02`, but touches install/inspect paths — do it with fresh attention |
| 3 | `RL-01`, `VR-01` | needs the `artifacts:` config surface designed before the probe is written |
| never | C12, plus everything in §5 | project-specific or class-shaped, not check-shaped |

## 7. What this file leaves open for the next curation

Not questions about the rules above — those are decided. These are the things one project could not settle, and the
next project with a different shape should test:

1. **Does a false accusation cost more than a missed defect in every domain?** `HV-02` assumes yes: it is written to
   stop the instrument from convicting a product. In a safety domain the trade flips. Nothing in gobstack can decide
   that per-project yet.
2. **What is the cheapest honest form of "reachable in N actions"?** C8 stayed advisory because "reachable" has no
   shared definition. Gobigrams measured it as a checklist of six tasks; another product will measure it differently,
   and the second measurement is where the definition will come from.
3. **Does the release family survive a project that ships ten artifacts?** `RL-01` assumes one record file with one
   row per release. A monorepo with five packages will want a row per artifact, and the `artifacts:` config has not
   been designed against that shape yet — design it against the second project, not this one.

The general rule this file is built on: a lesson earns a row only when its failure has been *measured* somewhere,
and a rule earns a mechanism only when the mechanism can be proven red on demand.
